# S3-compatible storage

Parquex applies the same public object and Parquet APIs to `s3://` locations as
to local paths. Configuration belongs to each `Parquex.Location`; there is no
process-global backend switch.

## Location options

The S3 URI supplies the bucket and key or explicit listing prefix. Supported
options are:

- `:endpoint` and `:region`
- `:path_style` and `:tls`
- `:request_timeout_ms` and bounded `:max_retries`
- `:credential_provider`, either `:standard` or `:explicit`
- `:access_key_id`, `:secret_access_key`, and optional `:session_token` for the
  explicit provider
- `:max_range_bytes` and `:max_request_concurrency`
- `:multipart_part_size` and `:max_in_flight_parts`
- `create_only: :required`

Endpoints must be HTTP(S) origins without embedded credentials, and their
scheme must agree with `:tls`. Multipart parts are bounded from 5 MiB through
512 MiB. Credential-shaped fields are redacted by `Inspect`; native errors are
stable classifications and never include request URLs, headers, or provider
material.

The standard provider reads the normal AWS environment/provider configuration.
Explicit credentials are useful for isolated compatible services:

```elixir
{:ok, location} =
  Parquex.Location.new("s3://test-bucket/prefix/object.parquet",
    endpoint: "http://127.0.0.1:19000",
    tls: false,
    path_style: true,
    credential_provider: :explicit,
    access_key_id: System.fetch_env!("S3_ACCESS_KEY_ID"),
    secret_access_key: System.fetch_env!("S3_SECRET_ACCESS_KEY")
  )
```

## Bounded reads

`Parquex.Object.read_range/3` rejects a request larger than the location's
`:max_range_bytes`. Parquet opens fetch the footer and metadata through those
ranges, then fetch only projected column data as batches are demanded. The
native request store limits concurrent HTTP requests to
`:max_request_concurrency`; retries and each request timeout are bounded by the
location.

The read buffering envelope is approximately:

```
prefetch_depth * decoded_batch_size
+ max_range_bytes * max_request_concurrency
+ bounded Parquet metadata
```

`Parquex.Stream.stats/1` reports range request counts, bytes, and the largest
range. Cancellation and owner exit signal in-flight remote futures before
native resource cleanup.

## Multipart writes and publication

The Parquet encoder writes incrementally into fixed multipart parts. At most
`:max_in_flight_parts` parts are being uploaded while one part is assembled, so
the transport limit reported by `Parquex.Writer.stats/1` is:

```
multipart_part_size * (max_in_flight_parts + 1)
```

This is in addition to one bounded input batch and bounded Parquet encoder
state. Multipart completion begins only after the encoder writes a valid footer.
Parquex then performs conditional create-only publication from its unique
staging key. A destination conflict leaves existing bytes unchanged. Backends
that cannot provide the conditional operation return `:unsupported`; Parquex
does not silently replace the object.

Failure or cancellation aborts the active multipart upload and removes owned
staging where supported. A cleanup failure does not replace the primary error.
Publication is not an exactly-once transaction: a transport failure around
completion can require the caller to reconcile with `Parquex.Object.head/1`.

## Project-owned RustFS tests

The root `docker-compose.yml` pins RustFS and the bucket-initialization image by
digest, binds test ports only to localhost, and uses disposable test-only
credentials and storage. The authoritative command is:

```sh
bin/qa_check.sh
```

That command validates Compose, waits up to 45 seconds for `/health/ready`,
creates the isolated bucket, runs the complete suite, emits service diagnostics
on failure, and tears down containers and volumes through an exit trap. It does
not depend on the sibling `RUSTFS_TOOL` directory.

For manual development only, a sibling checkout may be started and stopped with
`../RUSTFS_TOOL/bin/restart_rustfs.sh` and
`../RUSTFS_TOOL/bin/stop_rustfs.sh`. Configure a location explicitly for the
endpoint and credentials exposed by that tool. These scripts are optional,
machine-local conveniences; package builds, tests, CI, and the release gate
never invoke them.
